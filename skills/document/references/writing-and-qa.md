# 表达与交付检查

## 写到什么程度

读者需要看懂：什么情况下发生、玩家做什么、画面如何反馈、资源或进度怎样变化。按模块实际内容组织，不给每个按钮机械地套五个小标题。

- 有时间顺序，用步骤。并列条件和例外，用要点。
- 一个模块内容较多时，按“显示与入口、操作与结果、特殊情况”等含义分组；无内容的组不写。
- 表格中的描述同样分组，不把几个流程挤进一段。
- 同类棋子、障碍、任务或商品使用同一顺序；不同机制不强求完全相同的字段。
- 概述说主流程，模块说完整规则，界面表说显示与交互。引用已讲过的规则，避免重复三遍。

## 用普通话讲清逻辑

以下只示范措辞；只有资料包含对应规则时才使用。

| 冗长或难懂的说法 | 简明写法 |
| --- | --- |
| 通过配置化能力实现不同用户分层下差异化的活动资源投放 | 按玩家R分层读取系数，计算本次获得的活动体力。 |
| 对重复交互进行幂等处理，保障奖励结算一致性 | 重复点击只发放一次奖励。 |
| 按顺序执行状态恢复并避免重复消费随机序列 | 重新进入后保留本批结果，不再扣券或读取下一批。 |
| 完成条件满足后进行相应界面刷新与反馈 | 目标集齐后，任务条变绿并显示领取按钮；奖励需要玩家点击领取。 |

删除“形成闭环、赋能、提升体验”等不提供新规则的句子。若原稿明确写了活动目的，保留真实目的，不因精简而删掉。

不要过度展开按钮常识；有实际影响时才说明关闭后返回哪里、保留哪些状态、是否打断操作。遇到未知反馈，不擅自设计动画时长、镜头、音效或提示文案。

## 保留容易混淆的区别

- 目标完成、奖励可领取、奖励到账是不同阶段，不能统称“已完成”。
- 拥有道具、安装道具、提交道具可能对应不同事件，不能为了简短合并。
- 进度分母说明统计的是节点、数量、种类还是已领奖数。
- 倍率可能改变次数、消耗、等级或数量，按当前机制说明，不按“倍率”一词推断。
- 图鉴、任务手册、收藏可能采用不同计数和领奖规则，不因都是收集界面就互相照抄。

## UE与Word

有真实UE时使用编号图，表内编号与控件对应。显示状态和动作后的反馈放在相关模块；不能拿旧截图表示新逻辑，也不为了凑图擅自制作UI。

新建Word优先复制选定参考的工作副本，保留适用的页面、标题、表格、列表、页眉页脚和水印；替换主题内容及不适用图文。纯新类型没有合适底稿时可沿用已观察到的样式组织内容，无需强套独立合成线目录。

修改Word时不要整段覆盖含图片的空文本段落，避免破坏图片及链接关系。标题用标题样式，列表用原生编号。清理失效目录与章节引用；不复制导出文件中的“该类型内容暂不支持下载”等占位提示。

## 交付前检查

1. **范围**：每个功能都能对应当前资料或用户明确要求，没有因类型参考而多出商店、图鉴、补偿、引导等。
2. **逻辑**：名称、计数、消耗、分段、手动/自动、奖励到账和活动结束时机在图文与配置间一致。冲突仍列为待确认，没有擅自裁定。
3. **配置**：存在实际表头；每个字段说明用途和适用口径；必要单位、对应关系、公式与读取顺序齐全。没有用“读配置”掩盖规则缺口，也没有猜最终字段名。
4. **简洁**：同一规则只完整解释一次；没有程序实现方案、空标题或无用图示列。
5. **案例清理**：核对旧活动名、对象、周期、数值、图片、链接。当前活动实际使用的词不应被盲目删除。
6. **版式**：Word全页渲染检查，修正截断、窄列、标题孤行、异常空白、错位和模糊图。最后一次修改后重新渲染，确认所有最终页面。

只交付本次需要的成品；分析、来源记录和渲染中间文件留在工作目录。说明无法完成的检查，不虚报验证结果。
