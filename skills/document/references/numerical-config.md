# 数值逻辑配置

## 目标与边界

配置说明用于让策划和程序知道“哪些内容需要可配、分别控制什么、读取后怎样影响玩法”。它不是程序最终表结构。

功能已有分段消耗、任务目标、奖励、系数、档位、序列等需求时，即使数值未定，也应给出必要表头和字段说明。只有简单固定规则、不涉及配置时，不为凑格式新建表。

- 原稿已有表，优先整理原表；只为表达已有逻辑补足必要字段语义，不额外设计功能。
- 采用中文业务表头即可。原稿已有英文名时可附上参考；用户未要求时不必为所有字段新造英文Key。
- 字段类型、分隔符、ID编码、表名与枚举代码不是默认必填。需要区分数字、列表或多对象关系时用普通话说明即可。
- 单张表能清楚表达时不强拆。任务组与多个目标、玩具与品质转化等已有一对多或复用关系，可以沿用原稿分表。
- 不加日志、版本控制、审计、事务号、接口、缓存、数据库索引等实现字段。玩家当前余额、已领状态和序列读取位置属于进度记录，不直接当作策划配置列；如需初始化，只说明初始值配置。

## 每张配置表的交付内容

1. **用途与一行含义**：一句话说清表控制什么、每行代表什么。
2. **实际配置表头**：直接列可填写的列名，不能仅交付“字段／说明”而没有实际表头。
3. **字段说明**：逐项解释控制对象、单位、读取或生效时机、与其他字段的关系。仅在相关时补充空值、分段、范围与特殊值的业务含义；未知含义标待确认。
4. **必要读取规则**：表本身表达不了的计算顺序、取整、目标达成或序列推进。正文已写完整时引用该处，不重复长文。

值未定时在对应配置位置写“待定”；规则缺失时写“规则待确认”。二者不能混用。“数量待定”允许先写完整流程，“如何计算待确认”则不能伪装成已有公式。

不强制每表加示例。需要说明多段或多项对应关系时可用一行示意，明确标“结构示例，非正式数值”，不用随机业务ID假装已配置。

## 示例一 清障节点

适用：当前活动已写清障、分段掉落及剧情或手册关联。来源为清图稿9.2.2.1；字段取舍以本活动为准。

用途：配置各节点的消耗、产出及关联结果，每行一个节点。

**实际表头：** `节点ID｜各段活动体力消耗｜各段奖励｜剧情ID｜障碍物类型｜任务手册进度`

| 字段 | 详细说明 |
| --- | --- |
| 节点ID | 标识场景中的具体节点，供地图对象读取。不替程序规定ID位数或编码段。 |
| 各段活动体力消耗 | 按清除顺序填写每段需要的活动体力，单位为点；单段填一个值，多段填按顺序排列的值。原稿空值用于剧情直接领取节点，只有沿用此含义时才能这样写。 |
| 各段奖励 | 与消耗段逐段对应，描述该段成功后获得的奖励及数量，可引用已有奖励配置。某段无奖励应明确标无奖励，不能跳过该段导致错位。原稿包括扭蛋券产出。 |
| 剧情ID | 指向节点清除后触发的剧情；原稿空值表示不触发剧情。多段障碍在何段触发需按当前规则说明，不能靠ID格式推断。 |
| 障碍物类型 | 表示是否为剧情类对象；原稿1为剧情、0为非剧情，只是当前参考编码。不能凭此标签自动认定剧情完成或直接加剧情进度。 |
| 任务手册进度 | 表明关联的任务或目标及本次增长量。说明是在清障成功、修复成功还是后续互动成功时增加；触发尚未统一时标待确认。 |

没有剧情或手册的清障活动，去掉最后相关列。若本活动只有末段发奖，按明确的末段规则写，不沿用此例假定每段发奖。下划线、竖线等序列分隔符交由研发模板决定。

## 示例二 分R订单体力系数

适用：当前需求已说明通过订单经验换算活动体力。来源为清图稿9.6.1。

用途：为不同R层配置订单体力系数，每行一组适用R标签。

**实际表头：** `配置ID｜适用R标签｜活动体力系数`

| 字段 | 详细说明 |
| --- | --- |
| 配置ID | 标识本条系数配置；研发现有模板无需该列时可省略。 |
| 适用R标签 | 本行覆盖的玩家层级，可以按当前需求填单层或多层。层级重叠或未命中时采用哪个系数，原稿未说明，不能默认取第一条或系数1。 |
| 活动体力系数 | 玩家完成订单时，与该订单经验相乘，用于计算本次活动体力。系数具体值按正式数值确认，不把示例值设为默认。 |

**已给出的公式：** 本次订单活动体力＝订单经验×对应R层系数。

**尚需确认的口径：** 取整方式、分层读取时点，以及多条命中或未命中的处理。只在实际要定稿该机制时确认，不补造兜底规则。

集卡稿的金币需求系数不是此表用途。集卡可用`R分层｜金币需求系数`两列，分别说明适用层级和控制的需求系数；完整公式应用对象未确认时不照搬上述公式。

## 示例三 任务链节点

适用：当前活动已说明按资源量顺序完成节点并发奖励。表头是根据集卡稿现有需求整理的参考，不声称原稿已有同名配置表。

用途：配置顺序节点的需求和奖励，每行一个节点。

**实际表头：** `节点序号｜金币需求｜奖励配置｜是否为大奖节点`

| 字段 | 详细说明 |
| --- | --- |
| 节点序号 | 决定节点推进与奖励托盘补入顺序；可直接沿用项目已有节点标识，不额外设计另一套ID。 |
| 金币需求 | 完成该节点所需金币。必须说明是本节点独立需求还是全链累计门槛、是基础值还是套用R系数后的值；资料不明时先确认，不自行选择。 |
| 奖励配置 | 该节点达成后可领取的奖励及数量，可引用已有奖励表。这里配置奖励内容，不改变玩家主动领取的流程。 |
| 是否为大奖节点 | 标明界面用于展示最终大奖的节点。不能自动当作最后节点标记，除非当前需求明确两者相同。 |

**表外规则：** 有效金币来源、溢出推进、连续完成多档及最终节点领奖处理按当前文档说明。原稿取整为小于100取到个位、至少100取到十位并四舍五入，但要先明确在哪一步使用，才可代入公式。

## 其他已有配置的最小字段选择

以下用于查漏，只在当前功能存在时选用；不是每个活动都要生成的表清单。正式输出仍需逐字段说明，不能只复制本表作交付。

| 配置对象 | 可采用的实际表头 | 字段说明需要讲清的重点 |
| --- | --- | --- |
| 任务组 | 任务ID／任务名称／任务类型／显示顺序／依赖任务／奖励配置 | ID关联哪些目标；普通或全收集；顺序大小含义；依赖判定是已收集还是已领奖；奖励内容及领取条件。来自ManualTask。 |
| 收集目标 | 目标ID／所属任务／展示物品／收集事件／触发来源／所在地图／定位点／需求数量／显示顺序 | 每个目标由哪个成功事件计数，来源对应哪一对象；地图和定位只在有定位功能时保留；数量按件还是种类。来自ManualTarget。 |
| 剧情节点 | 点位／前置条件／完成操作／场景结果／任务关联 | 一行一个剧情点；前置与完成分开；明确哪一步计剧情或手册进度。对话文本按内容稿引用，不擅自补剧情。 |
| 扭蛋奖励序列 | 房间奖励池ID／有序奖励内容 | 本例按房间ID顺序抽取；内容为有顺序的奖励及数量，单抽读一项，批量逐项读。不能把有序列表写成随机权重池。最后一项之后如何续接未写时不自动循环。来自GachaMain。 |
| 玩具基础 | 玩具ID／品质ID／所属收藏组ID | 玩具ID判断是否已拥有；品质关联重复转化；收藏组关联收集进度。来自GachaToy。 |
| 重复转化 | 品质ID／转化奖励／转化数量 | 哪个品质的重复玩具适用；转成什么；每件重复转多少。首次获得不套用重复转化。来自GachaQualityConvert。 |
| 收藏组奖励 | 收藏组ID／奖励配置／组类型 | 普通组或全收集；组内对象由玩具表关联；全收集是否要求先领分组奖按当前规则，不自行添加依赖。 |
| 兑换商品 | 商品ID／奖励配置／扭蛋券价格／兑换上限／排序 | 一行一个商品；奖励为单次所得；价格为单次花费；本例上限指本期，-1不限次、正整数限次，0含义未给出；排序越小越靠前。来自GachaShop。 |
| 生成器成长 | 生成器等级／升级条件／产出序列／开放倍率 | 每档由何种首次获得或其他事件解锁；切换哪个序列；倍率开放与产出等级不混写。只选当前机制使用的列。 |
| 合成线 | 合成线或棋子标识／等级／获取方式／合成结果／关联奖励 | 原稿有主支线及等级描述；需说明同级同链条件及最终级结果。奖励列只在该等级有奖励规则时使用；不强制做成独立程序表。 |
| 倍率 | 倍率档位／资源消耗／产出规则／解锁条件 | 产出规则说明读取次数、数量或等级变化，避免只写“翻倍”；不足时是否降档按正文，不自动增加配置开关。 |
| 图鉴奖励 | 图鉴对象／单项奖励／合成线奖励／全图鉴奖励 | 按实际粒度选择对象或分组，奖励不要在每行重复配置同一个全图鉴奖；说明各层奖励条件及是否手动领取。无对应奖励层就删列。 |
| 活动体力参数 | 参数／配置值 | 只列原稿需要的初始值、恢复间隔、单次恢复量、恢复上限，分别说明点数或时间单位；“恢复上限”不等于奖励入账上限。不强拆成四张表。 |

皮肤、难度、开关等已有配置按同样方式说明业务含义。沿用项目已有配置时只描述本活动新增或改变的部分，不重建整个配置系统。

## 常见遗漏检查

- 只有字段名没有含义，或只有“奖励读配置”没有奖励对应对象。
- 一列既写奖励包ID又写直接奖励列表，未说明所表达的内容。
- 分段费用与奖励数量不对应；任务与目标、玩具与收藏组关系不清。
- 倍率只写消耗，不写是多次读取还是单次结果加成。
- 取整没说明对象、单位或发生在乘系数前后。
- 把“可配”误写成“可以任意改变规则”；把未写的概率、上限、保底或日刷新补进表。

发现上述问题时补清已有语义或指出缺口；不要借检查扩展玩法和程序架构。
