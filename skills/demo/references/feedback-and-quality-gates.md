# 反馈迭代与质量闸门

## 1. 变更登记

收到反馈后先写最小变更表，不直接改最后一个可见产物：

| 原规则 | 新规则 | 类型 | 影响产物 | 验收证据 |
| --- | --- | --- | --- | --- |
| `[填写]` | `[填写]` | 不变量 / 数值 / UE / 接口 | 需求 / Figma / 配置 / 代码 / 文档 | `[填写]` |

执行顺序：读取目标路径最新文件与 Git 状态 → 复现问题 → 更新规则源 → 更新受影响产物 → 自动与浏览器验收。用户指定目标目录时直接在该范围交付；无法写入时明确说明降级路径。

## 2. 阶段确认闸门

- `需求待确认`：只交付完整需求、假设和待确认项。
- `UE待确认`：只交付 UE/Figma、组件状态与尺寸审计；不制作正式 Demo。
- `Demo已授权`：以确认后的需求和 UE 为唯一输入，不回退到早期草图。
- `部署已授权`：检查仓库与发布配置；除非用户明确要求，不自行提交或推送。

用户反馈“质量不足以验证”时，先回到上一个未确认阶段，不在低质量原型上继续堆功能。

## 3. 规则不变量卡

按 [prototype-cognition.md](prototype-cognition.md) 先判断机制；以下仅记录并复核当前活动实际存在的项，不适用项不生成玩法：

1. 合成基数：二合、三合或其他；每一阶的精确公式。
2. 输入来源：活动直接赠送、主线订单、主线生成器、礼包或运营补偿。
3. 手动/自动边界：谁触发装填、发射、领取、升级与补位。
4. 库存边界：是否跨关、跨日、活动结束；满盘和溢出去哪。
5. 目标规则：总量、显示容量、视觉尺寸、队列方向、相邻组上限。
6. 随机规则：随机对象、权重、保底、连续上限、可复现 Debug。
7. 奖励职责：关卡奖励、图鉴、支线与礼包不得混用同一入口含义。
8. 特殊格状态：障碍、半解锁、蛛网或其他格子的触发位置、触发次数、预置棋子、可移动性、占用状态和转换结果。

这些字段发生变化时，至少同步需求、配置、Demo状态、体验说明和 QA。

## 3A. 障碍格与半解锁格验收

- 将 `完全障碍格 → 半解锁格（带预置棋子）→ 普通格` 实现为显式状态机，不用遮罩显隐代替真实交互状态。
- 完全障碍格不可放置、移动、合成或生成棋子；只响应规则指定的邻接合成事件。
- “四周”默认指上、下、左、右正交相邻，不包含斜角。配置必须说明一次合成影响一个还是全部相邻障碍、需要几次触发、连续合成是否重复计数。
- 完全障碍解除后，显示半解锁格及其预置棋子；该棋子不可移出。玩家拖入同链同等级棋子时完成一次正常合成，生成高一级棋子并将格子永久转为普通格。
- 不同链、不同等级、拖到空半解锁格、拖出预置棋子和重复事件均不得错误解锁；给出原位拒绝反馈。
- 验收初始可操作区、所有障碍的可达路径和随机产出最坏情况，避免玩家因缺少匹配棋子、无邻接合成位或满盘而永久卡死。
- 明确半解锁合成是否能同时触发相邻障碍、活动结束与重置后的格子状态、断线重连和重复点击幂等性。

## 4. 容量、尺寸与队列

- 分开配置 `total_count`、`visible_capacity` 和 `visual_size`；“最多有8个”不等于必须同时显示8个。
- 优先保持操作对象尺寸和点击热区稳定。空间不足时减少可见数量并使用后备队列，不为塞满配置上限临时缩小对象。
- 清除 N 个后只补入 `min(N, reserve_count, visible_capacity - visible_count)` 个；剩余不足时不补。
- 明确前推方向、排序稳定性和补位动画。内容变化不得改变面板、棋盘或主要按钮的位置。
- 若相邻同色最多为2，随机生成和补位后也必须校验；不能只校验首屏静态配置。

## 5. 随机但防卡死

- 不把“随机”实现为写死序列，也不把“防卡死”实现为每关正好发够全部材料。
- 当资源来自主玩法订单等上游系统时，活动只定义接入事件和分配算法；Demo 用 Debug 模拟“完成订单”，不伪装成活动进关赠送。
- 优先配置目标组、颜色计数、池或权重，再在运行时生成顺序；教学关可固定，普通关应有可观察的排列变化。
- 随机产出至少定义：基础权重、需求修正、连续同色上限、累计色差/缺色保底、跨关库存和溢出队列。
- 数值使用公式或区间：`预计订单数 × 单次产出`、库存折算、期望缺口和最坏偏差。没有真实数据时标为 Demo 基准，不声称是线上结论。
- 防止重进关卡、重连或重复点击刷取彩蛋和奖励；记录已领取次数或唯一事件 ID。

## 6. 随机系统验证

除单次成功路径外，执行批量约束测试：

- 序列：长度、颜色计数、相邻上限、奖励对象位置、首尾限制、可见容量。
- 产出：连续同色上限、累计偏差、最低可用量、待放区峰值、跨关剩余。
- 经济：关卡奖励幂等、支线等价值、资源总量与上限。
- 重置：初始状态深度一致；随机种子或 Debug 能复现问题。

默认至少运行数百轮；复杂权重运行 1,000 轮或更多。报告轮数、最坏样本、是否通过和真实数据仍需验证的部分。蒙特卡洛只能发现实现风险，不能替代真实玩家数据。

## 7. UE 与视觉验收

- 用户截图表达的是结构与意图证据；先确认要保留和删除的区域，再写入 Figma 或代码。
- 同链不同颜色、不同等级的棋子必须有形状、纹样或文字差异，不能只靠轻微换色。
- 奖励预览、图鉴和礼包使用不同标题、进度和行为；入口位置可以复用视觉语言但不能混淆职责。
- Debug 放在独立低权重区域，模拟上游事件、指定边界、跳关和重置；不冒充正式玩家入口。
- 浏览器按目标移动端尺寸截图，检查裁切、滚动、固定尺寸对象、弹窗密度和点击热区。
- 单屏活动的弹窗状态必须带同一主界面背景或明确的父子节点关系；Figma 为展示交互状态而复制画板时，命名为 `主界面｜Modal-状态`，不得误写成新的玩家页面。
- 自动触发动作在弹窗出现后直接进入请求中或动画中；结果态只保留关闭、继续或说明性操作，不增加重复的开始按钮。
- 不放回抽奖逐项验收：抽中条目已从剩余集合移除、对应扇区/条目压暗、已领取标记可见、指针后续不会落入该项、重进仍保持压暗。
- 图鉴逐项验收：总进度奖励、分类奖励、4列或目标端可读网格、链路顺序、NEW状态、锁定占位、滚动边界；图鉴不得承载礼包或抽奖确认职责。
- 特殊格逐项验收：实际棋盘至少出现一个完全障碍和一个半解锁示例；半解锁显示预置棋子且链路与需求一致；普通/半锁/障碍在灰度截图下仍可区分。
- 物件参考逐项验收：先列出轮廓、分割线、材质和关键比例，再对照截图；只匹配配色不算还原。
- 生成动效逐项验收：点击后装置立即响应、内部对象确实运动、入口在结算期间禁用、飞行起点是视觉出口、终点是真实目标格、倍率产出错峰、落点有收尾反馈、临时特效最终清理。
- 用浏览器读取动画名或中间状态证明动效真实运行，不能只凭静态 CSS 声称完成；同时验证动画前后资源守恒和目标格数量。
- 在 390px 主目标宽度与 320px 窄屏分别检查横向溢出和格子点击尺寸；可操作棋盘格在最窄验收宽度仍应达到约 44px，若做不到必须调整外边距、面板内边距和格间距，而不是缩小棋子文字到不可读。

## 7A. Deno 部署验收

- 使用最新 Deno Deploy 配置模型；静态项目包含可解析的 `deno.json`，`runtime.type`、`cwd` 和 `spa` 与实际目录一致。
- 未使用的 Install/Build Command 为空；配置中不存在未生成的 `dist`、本机绝对路径、Node 专属启动参数或第三方运行依赖。
- 本地 HTTP 分别请求 `/`、样式、入口 JS、规则模块和 `deno.json`，均返回 200 与正确 MIME；再检查浏览器控制台无 error/warn。
- README 与独立部署说明必须给出控制台手工兜底值，并明确完整上传 `src/` 等嵌套目录。

## 8. GitHub Pages 发布完整性

发布前执行：

1. 运行 `scripts/validate_web_demo.py <project-dir>`；Git 仓库交付再加 `--require-git-tracked`。
2. 检查 HTML/CSS/JS 的本地引用都存在；禁止 `file://`、本机绝对路径和会破坏项目站点子路径的 `/assets/...` 根路径。
3. 用 `git status --short` 查看修改与遗漏，用 `git ls-files` 确认 `src/`、样式、图片和配置均已包含。
4. 从目标仓库目录启动服务器；分别请求首页、入口 JS 和关键资源，检查 HTTP 200 与 MIME。
5. 在浏览器完成核心循环、随机/容量边界、重置和控制台错误检查。
6. 只有实际提交并推送后才能声称远端已更新；本地修复完成时明确提示用户仍需 Commit/Push。

最常见失败是只上传根目录文件而漏掉 `src/`。不要仅因为本地另一份工作区能运行，就推断目标仓库完整。
