# Figma UX 工作流

## 1. 输入检查

- 明确是新建文件还是修改现有文件。
- 有现有 Figma 时先读取最新页面、节点、变量、组件和用户改动。
- 有截图时把截图当布局/意图证据，不自动把其中所有文案和规则当成最终需求。
- 收到多轮反馈时先列出删除、移动、保留和新增区域；以用户最新标注覆盖旧截图，但保留未被修改的已确认部分。

## 2. 工具前置

- 先读取 [portable-runtime.md](portable-runtime.md)，按能力映射当前环境的 Figma MCP 工具，不假设工具名称一致。
- 新建文件、读取设计、执行写入和截图验收可能由不同工具承担；逐项确认权限。
- 当前平台若提供 Figma 专用说明、技能或强制前置，先完整读取并遵守。
- 不使用当前工具未支持的 Plugin API；遵守分阶段写入、限量调用和验证要求。
- 没有可写 Figma MCP 时，只交付 UX 规格和可实现的本地线框，不声称已修改 Figma。

## 3. UX 计划

在写入前列出：

- 页面/状态地图。
- 重复组件与 Variant。
- 数据和交互状态。
- 动效触发与持续时间。
- 规则脑图到页面控件的映射。
- 系统策划需求 ID 到页面、组件、Variant、异常状态和文案 key 的映射。

先建基础变量与复用组件，再组装页面。不要为了“像成品”而提前锁死最终美术风格。

默认只规划一个主界面；图鉴与 INFO 可使用同屏模态层，其他反馈优先使用自动淡出的轻弹板或 Toast。用户明确要求多页面时再扩展，并说明导航与状态维护成本。

## 4. Merge 活动重点

- 盘面尺寸、行列和单格点击区必须固定，内容变化不得撑大盘面。
- 合成链应能完整查看；长链可水平拖动或滚动，并高亮当前最高节点。
- 资源库存、单次消耗、倍率和产出数量要同时可读。
- 自动升级与手动升级必须二选一，除非规则明确说明两种入口。
- 动效服务状态变化；频繁循环避免强制领奖或重复确认弹窗。
- 图鉴、奖励、Debug 和异常提示不得遮挡核心操作或引入不必要步骤。
- 覆盖活动开启、结束、停留页面跨结束时间、未领奖、断线重连和本地时间异常等生命周期状态。
- 对棋盘、生成器、待领奖区、图鉴、礼包和资源获取分别呈现需求文档定义的可见状态；纯后台配置不强行制作无意义画面。

## 5. 验收

逐屏检查：

- 尺寸、间距、字体、截字、重叠和滚动范围。
- 组件实例、变量绑定、图层命名和点击热区。
- 初始、进行中、成功、失败、满盘、资源不足、活动结束状态。
- 脑图规则与页面文案/按钮是否一一对应。
- 每个玩家可见需求 ID 是否至少映射一个节点或状态；Figma 是否擅自新增需求文档中没有的消耗、奖励或阻塞步骤。

截图或结构审计后再交付节点链接。若无法连接 Figma，明确阻塞，并只交付本地线框或页面规格，不假装已经写入。

用户要求“确认 UE 后再做 Demo”时，交付节点、状态清单和截图后停止。只有收到明确确认才把该版本作为代码输入；不得用未确认 UE 生成所谓最终版 Demo。
