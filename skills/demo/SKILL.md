# 玩法与活动原型工坊

## 目标

把活动点子推进为六个可插拔但保持一致的交付层：`论证 → 规则脑图 → 系统策划需求 → Figma UX/UE → Web Demo → 通俗体验说明`。规则脑图定义方案边界，系统策划需求把边界展开为可实现、可配置、可测试的需求原子；后续修改先更新已启用的规则源，再同步后续产物。

## 先判断目的与制作规模

先读取 [prototype-cognition.md](references/prototype-cognition.md)，分别判断本次目的、系统归属、实际机制与复杂度，再选择必要模块和交付层。适用于小功能、轻玩法与多系统活动，不能把“独立玩法”默认解释为独立合成线或大型活动。

核心流程保持理解、对齐、规格、表达、实现、验收；不强制每步都生成独立文件。已有规则可复用，局部修改只补相关规格，按明确要求设置阶段确认点。

## 活动类型路由

开始概念设计前读取 [gameplay-event-knowledge.md](references/gameplay-event-knowledge.md)，按“核心行为发生位置、资源所有者、是否新增独立状态空间”选择一个主类型：

- `A 主循环行为映射型`：订单、体力、合成或登录等既有行为只映射为活动进度、收集或 DIY。
- `B 主盘规则变体型`：仍在主 Merge 盘操作，但临时改变掉落、订单、目标或格子状态。
- `C 独立合成线/活动盘型`：新增独立棋盘、棋子链、库存和活动资源。
- `D 独立非合成玩法型`：新增非 Merge 的核心操作、单局或探索空间；复杂度另行判断。
- `E 社交/社区层`：分享、协作或排行；通常叠加在 A–D 上，只有玩家关系本身承担主要循环时才作为主类型。

再添加 `任务/里程碑/收集/DIY/随机奖励/外显/分享/付费补速` 等表达标签。类型决定系统边界，机制和复杂度决定验收深度，标签补充局部规则与表现；不要因为活动包含换装、分享或弹窗就误判为独立小游戏。

本 Skill 的核心流程不绑定模型厂商。开始前读取 [portable-runtime.md](references/portable-runtime.md)，发现当前代理的文件、网络、浏览器、Figma MCP 与执行能力，并选择对应适配方式。不要调用不存在的工具，也不要把平台专属工具名写进规则源。

## 强制判断原则

核对当前需求的可行性与内部一致性，不把推测当成事实。以下检查按本次目的和范围选用，不在局部改动中展开无关评审：

1. 找出错误前提、规则矛盾、因果倒置和无法成立的边界。
2. 找出会改变方案方向的信息缺失；仅在必须由用户决定时提问，其余以明确标注的假设继续。
3. 将陈述区分为 `事实`、`推测`、`主观判断`、`待验证`。不得用语气强弱代替证据。
4. 涉及数字、行业结论、竞品表现或平台规则时，尽量查证一手来源；无法查证时给公式、区间或验证方法，不伪造精确值。
5. 不同意时直接说明结论、依据、风险和至少一个替代解释或方案。
6. 只指出会影响本次判断的遗漏变量；涉及分层、库存、成本、随机或长期经济时再检查相应风险，不给单功能修改附加整套经营分析。

### 概念设计两门槛与六问题

在输出玩法概念、脑图、需求、UE 或 Demo 前，先完成两道门槛判断：

1. **契合门槛**：确认方案符合当前产品定位和本次原型目标。依附 Merge 产品时检查与合成主循环的关系；独立玩法按自身核心循环判断，不强制加入合成或主线订单。
2. **落地门槛**：确认开发、美术、配置、QA、工期和体验风险处于当前项目可接受范围；缺少项目约束时给出最小版本和成本变量，不擅自判定“成本可接受”。

再逐项回答六个问题：

1. 玩家能否在 10 秒内理解目标、操作和直接结果？
2. 单次核心操作是否有足够强、且与事件价值匹配的反馈？
3. 当前操作的目标与完成条件是否清楚；需要持续成长时，中长期目标是否成立？
4. 是否与目标用户、产品定位和题材匹配？
5. 是否有足够的内容及数值扩展空间，而不是依赖重复堆等级？
6. 是否有竞品、用户研究或原型数据支持？若没有，标记 `待验证`，给出最低成本的原型或研究方法，不伪造证据。

概念阶段先给最小可玩骨架：`一个核心行为 + 清晰即时反馈 + 可判断的完成/继续条件`；中长期成长只在任务确有需要时加入。先说明最小版本，再把额外系统列为可选扩展；不要为了显得丰富而同时加入多个经营子系统。任一门槛不通过时停止下游正式制作，说明不通过原因并给出至少一个更低成本或更契合的替代方案。

先输出一段简短的“审查结论”，再开始制作。高风险断点未解决时，不进入 Figma 或编码；可逆且不改变方向的缺口用假设继续。

详细审查表见 [critical-review-gate.md](references/critical-review-gate.md)。

## 策划到 Demo 的表达契约

- 写策划或修改上游规格时读取 [planning-clarity-and-ue.md](references/planning-clarity-and-ue.md)：先对齐流程与节奏，面向程序和下游部门，分类说明触发、操作、表现、结果和边界。正式正文不粘贴对话记录或内部需求矩阵。
- 新建/整体重写的策划默认聚焦功能范围，AB 测及后置规划章节按明确要求启用；不会因此省略实现所需规则或停止必要测试。
- 修改地图、收集、奖励预览、镜头或连续动效时读取 [interaction-feedback-contract.md](references/interaction-feedback-contract.md)。只对当前机制适用的交互建立过程与验收，不把案例的具体玩法固化为所有 Demo 的要求。

## 反馈与确认契约

- 把用户最新明确反馈作为当前事实源；先生成“原规则 → 新规则 → 影响产物 → 验收”的变更清单，再修改文件。
- 区分 `核心不变量`、`可配置数值`、`UE表达`、`上下游接口`。不要用改文案掩盖规则变化，也不要用 Demo 便利逻辑替代正式资源来源。
- 读取 [feedback-and-quality-gates.md](references/feedback-and-quality-gates.md)，用于多轮反馈、随机产出、固定容量队列、数值重调、现有仓库修改和 GitHub Pages 发布。
- 用户指定“先需求、再 UE、确认后再 Demo”时，将每个“确认后”视为硬闸门；未收到明确确认不得提前进入下一阶段。
- 反馈推翻旧结论时，先更新唯一规则源与结论状态，再同步 Figma、配置、代码、体验说明和 QA；不得只修最后一个可见产物。

## 工作流

### 阶段选择与跳过规则

- 开始时根据用户目标建立阶段清单，每个阶段标记 `启用 / 跳过 / 已有产物复用`。不要强迫用户走完整流程。
- 为用户明确要求确认的阶段标记 `等待确认`；等待期间只修当前阶段，不创建后续正式产物。探索性草稿必须明确标记且不得冒充已确认结果。
- 批判性审查不可跳过，但可只在内部执行并用一句结论交付；脑图、需求文档、Figma、Demo、体验说明均可独立启用。
- 用户明确只要某一产物时，只完成该产物必需的上游信息，不擅自扩大范围。
- 跳过中间阶段时，用最小“接口契约”连接前后：列出本阶段本应提供的规则、状态、布局或验收信息，并将缺口标为假设。
- 复用已有产物前先读取最新版本，不以本 Skill 的默认模板覆盖用户已经确认的设计。
- 最终报告列出执行、复用、跳过的阶段，以及跳过对准确性、可维护性和验收的影响。

### 0. 还原点子并建立唯一规则源

- 识别目标玩家、活动周期、核心目的、主循环、主线牵引、资源来源/消耗、奖励、付费承接、开发限制和成功指标。
- 使用 [gameplay-event-knowledge.md](references/gameplay-event-knowledge.md) 记录 `主类型 + 表达标签 + 判定依据`；活动方向变化时先重新分类，再调整需求深度。A 类不得自动补独立盘，C 类不得省略盘面、库存与防卡死，E 类不得把分享设为核心奖励的默认前置。
- 产品实际涉及 Merge 时再读取 [merge-meta-knowledge.md](references/merge-meta-knowledge.md)，只采用相关条目；其他玩法不继承合成基数、盘面容量或主线订单规则。
- 将未知项标为假设，不把知识库经验当成项目事实。
- 若用户提供现有文档、Figma 或 Demo，先读取最新版本；不得按旧对话中的版本覆盖用户后续修改。
- 建立 `事实 / 假设 / 决策 / 待验证` 四类记录；跨产物只引用已确认决策，避免 UX 或代码把假设悄悄固化为规则。
- 建立“规则不变量卡”，先记录本次核心操作、手动/自动边界、输入来源、结果和状态生命周期；存在合成、库存、随机、队列或收藏时再增加合成基数、链路层级、跨关库存、随机/保底、显示容量与总量、奖励与图鉴职责；存在障碍格、半解锁格、蛛网格或其他特殊格时，额外记录 `格子状态 → 触发位置/次数 → 棋子限制 → 转换结果 → 是否可移动/占用` 的完整状态机。每次反馈后逐项复核，防止把二合写成三合、把外部订单产出写成进关赠送，或把格子解锁误写成棋子解锁等方向性错误。

### 1. 先交付 Markdown 思维脑图

- 使用 [idea-mindmap-template.md](references/idea-mindmap-template.md) 的标题层级。
- 覆盖核心目的、核心操作、规则、反馈与必要边界；资源、成长、商业化和数据验证等分支仅按本次机制与范围启用。
- 默认先给简洁骨架，每个节点只写足以支持决策的内容；用户要求完整策划案时再展开数值、状态和边界。
- 写成可被 XMind、幕布或常见 Markdown 脑图工具读取的层级结构。
- 在规则脑图确认前，不把未经确认的装饰性想法扩展成核心机制。

### 2. 生成系统策划需求文档

- 读取并使用 [system-requirements-template.md](references/system-requirements-template.md)。模板来自已验证的 Merge 活动需求颗粒度，但不得照搬任何示例活动的具体规则。
- 在项目工作规格中为关键规则保留需求 ID，覆盖实际需要的触发、前置、消耗、处理、结果、反馈、恢复与验收；埋点等扩展字段按已启用范围记录。正式策划按功能重组，不逐条粘贴内部字段或 N/A。
- 覆盖活动目的、流程、开启/关闭、实际存在的界面、系统、资源、奖励与边界；只为当前机制补充棋盘、生成器、收集等模块。多语言清单、埋点、AB 等后置规划按需启用；QA 属于制作验证，不必写进正式策划。
- 禁止只写“同其他活动”；复用时给出可定位来源、版本和本活动差异。
- 建立跨产物同步矩阵：`需求 ID → 脑图节点 → Figma 节点/状态 → Demo 模块 → 配置字段 → 埋点 → QA 用例`。
- 进入 UE、程序评审或 Demo 前，必须有足以实现的规则规格；优先复用已确认文档，只补当前缺口。只要求局部改 Demo 时，在项目工作记录补规则与验收即可，不强制另交一份完整策划。

### 3. 使用 Figma MCP 生成或修改 UX

- 读取 [figma-ux-workflow.md](references/figma-ux-workflow.md)。
- 修改现有文件时以最新 Figma 节点为准，保留用户已修改部分，只做范围内变更。
- 按 [portable-runtime.md](references/portable-runtime.md) 映射当前环境的 Figma MCP 工具；若平台有强制前置说明或技能，先完整读取并遵守。
- 先做页面地图、组件清单和状态清单，再写入 Figma。
- 用需求 ID 标注页面、组件、Variant、弹窗和异常状态；保证玩家可见需求都能反查到需求文档。
- 使用组件、变量和清晰命名；逐屏截图或结构审计，检查尺寸、溢出、点击热区、字体、状态覆盖和规则一致性。
- UX 是交互规则的表达，不得悄悄发明脑图中没有的消耗、奖励、弹窗或确认步骤。
- 用户明确要求单屏或小组件弹窗时，把不同过程画板标记为同一主界面的状态预览，不得实现成独立页面；弹窗下方应保留主界面上下文，并在页面地图、需求与状态名中统一写成 `主界面 + Modal`。
- 用户明确动作在入口打开后自动发生时，不得再添加“开始”“确认抽取”等冗余按钮。至少展示 `触发/请求中 → 结果 → 恢复`，并保证关闭、重进和重复点击不改变已确定结果。
- 不放回奖池的结果态必须同时表达“已抽结果”和“不可再抽”：抽中奖项的扇区或条目压暗/灰化并带已领取标记，未抽奖项保持可识别；不得只改剩余数字。
- 图鉴优先采用“顶部总收集奖励与进度 → 分类奖励条 → 规则顺序网格 → NEW/已收集/未解锁状态”的层级。链路顺序、锁定占位和分类奖励必须在一个滚动容器中可追溯，不与礼包或转盘入口混用。
- 棋盘 UE 必须在实际盘面中展示被需求指定的特殊格，不得只放在图例或组件页。完全障碍、半解锁和普通格至少通过轮廓/纹样/封条/锁标记中的两种差异区分；半解锁格显示其预置棋子，若需求指定主线 B 棋子则不得替换为 A 链或无关占位。
- 用户给出物件轮廓参考时，先复现决定识别度的几何特征，再补品牌装饰。例如扭蛋参考包含圆形外轮廓、白色上盖和弧形分界时，不得退化成普通双色圆或标签色块。
- 用户明确删除或忽略入口时，从玩家主界面、页面地图、状态清单与需求同步矩阵中一并移除；不得保留无行为占位。
- 当前环境没有可写 Figma MCP 时，明确标记阻塞；继续产出平台无关的 UX 规格、页面地图与组件/状态清单，但不得声称已创建 Figma 文件。
- 用户跳过 Figma 或没有可写 Figma 能力时，读取 [default-single-screen-ue.md](references/default-single-screen-ue.md)，以该单屏交互规范直接推进 Demo；除非用户另有交互要求，不要临时发明另一套页面结构。
- 用户要求先确认 UE 时，交付页面、弹窗、空/满/锁定/随机状态与尺寸审计结果后停止；只有收到明确确认才进入正式 Demo。

### 4. 生成可部署的 Web Demo

- 读取 [web-demo-workflow.md](references/web-demo-workflow.md)。
- 同时读取 [feedback-and-quality-gates.md](references/feedback-and-quality-gates.md) 的配置、随机验证与部署章节。
- 已有工程优先原位修改；新建时可用 `scripts/scaffold_demo.py` 复用 `assets/web-demo-starter/` 的工程能力，再按实际机制替换示例界面和规则。不能因为起始模板含棋盘就给非合成玩法新增棋盘。
- 默认拆分为 `state`、`rules/game engine`、`components`、`main` 和样式；小型演示保持零第三方运行依赖。
- 必须实现最小可玩闭环、Debug 重置、关键状态反馈和边界提示。规则优先于视觉装饰。
- 上游系统拥有的资源必须通过清晰接口进入活动；Demo 用 Debug “模拟上游事件”，不得在进关时直接塞入刚好通关的资源，除非该赠送已被确认。
- 默认制作一个主界面；除图鉴和 INFO 外，奖励、升级、帮助、错误和确认优先使用渐入渐出的小弹板或 Toast。只有复杂内容或用户明确要求时增加页面。
- 按本次交付成熟度制作视觉；要求可体验成品时不交付后台卡片或无反馈线框。参考 [default-single-screen-ue.md](references/default-single-screen-ue.md) 的层级与反馈方法，仅采用适合当前机制的布局，不为套模板新增盘面、图鉴或成长系统。
- 主题生成动作必须形成可追溯的反馈链：`入口响应并锁定 → 状态引擎只结算一次并保存 → 来源装置与内部对象运动 → 已确定结果从明确出口飞向真实接收位置 → 到达反馈 → 恢复可操作`。接收位置可为棋盘格、资源计数或收集入口，以当前规则为准。例如扭蛋机至少包含机身或玻璃罩轻晃、罩内扭蛋错相抖动、旋钮反馈和出蛋口到目标格的弧线飞入；只让按钮缩放不算完整产出反馈。
- 动效不拥有规则结果。动画期间锁定重复入口；消耗、随机、落格和奖励由引擎原子执行；中断、减少动态效果或动画失败不得造成重复消耗、重复产出或结果变化。
- 飞入动效使用渲染后的真实来源/目标几何坐标，在独立的全屏反馈层运行；棋盘仍保持固定格子尺寸。落点棋子可同步隐藏或延迟显现，避免“棋子先出现、另一个装饰物再飞来”的双影问题。
- 必须支持 `prefers-reduced-motion`：缩短或取消大范围飞行和摇晃，但保留最终落格、结果文本和不可交互状态。
- 在代码注释、状态/规则命名或项目追踪表中保留核心需求 ID；未实现需求必须显式列出，不得用视觉占位冒充逻辑完成。
- 工程至少包含 `index.html`、模块化源码、`package.json`、`server.js`、`.nojekyll` 和用户 README；可直接上传 GitHub 根目录。
- 目标为 Deno Deploy 时，以当期 Deno 官方文档为准并优先交付零依赖静态站点：根目录提供 `deno.json`，使用 `deploy.runtime.type = "static"`、指向真实静态目录的 `cwd`，仅在确为 SPA 时启用 `spa`；没有生成目录时不得把 Static Directory 写成 `dist`，没有安装或构建步骤时必须明确留空。
- Deno 静态部署之外可提供 `main.ts` 动态回退入口，但只使用稳定的 `Deno.serve`、文件读取、MIME 映射和路径穿越防护；本地预览入口与 Deno 部署配置不得互相依赖 Node 专属 API。
- Deno 交付前解析 `deno.json`、逐个请求 HTML/CSS/入口 JS/关键模块确认 200 与 MIME，并在 README 中给出 `No preset / Static Site / 空 Install / 空 Build / 正确 Static Directory` 的手动兜底配置。
- Deno 目标必须在编码前确定为 `静态站点` 或 `Deno 支持的框架预设`，并按该目标选择工程骨架。不得把 vinext、Cloudflare Worker 或 Sites 专用产物当作标准 Next.js 工程上传给 Deno 的 `Next.js` 预设；Deno 会要求 `.next/standalone/package.json`，而 vinext 默认不会生成该目录。
- 若交付标准 Next.js：`package.json` 的 build 必须真实执行 `next build`，项目必须显式依赖 `next`，`next.config.*` 必须设置 `output: 'standalone'`，`deno.json` 必须声明 `deploy.framework: "nextjs"`。交付前从干净安装执行构建，并硬性检查 `.next/standalone/package.json` 与 `.next/standalone/server.js`；任一缺失即视为 Deno 不可部署，不得声称适配完成。
- 若现有工程是 vinext/Cloudflare/Sites，而用户要求上传 Deno，优先把纯前端 Demo 改为静态 Vite/HTML；确需 SSR 时转换为标准 Next.js 或提供 Deno 动态入口。只修改 Deno 控制台里的 Build Command 不能修复产物格式不匹配。
- 用户给出本机 Windows 路径但当前环境无法访问时，不声称已写入该路径；在可写工作区创建完整项目并明确让用户覆盖到目标目录。
- 修改既有 Demo 时先复现问题；锁定网格/容器尺寸，避免内容变化导致布局跳动。
- 运行 `scripts/validate_web_demo.py <project-dir>`，再进行可用的浏览器或 HTTP 冒烟测试。
- 随机序列、权重、保底或动态容量存在时，除浏览器成功路径外，运行约束测试或蒙特卡洛测试；报告轮数、不变量、最坏结果和仍未验证的真实数据假设。
- 若当前代理不能执行脚本，仍生成完整工程，并把未执行的验证项逐条列出；禁止把静态阅读描述成运行验证。

### 5. 生成通俗的 Demo 体验说明

- 读取 [demo-explainer-template.md](references/demo-explainer-template.md)，在 Demo 根目录生成 `Demo体验说明.md`。
- 用不参与项目的人也能理解的语言说明“这是什么、怎么玩、会看到什么、能验证什么、还没做什么”。
- 不堆叠策划、数据和程序术语；必须出现的词在第一次出现时用一句白话解释。
- 操作步骤、按钮名、状态和未实现项必须与当前 Demo 一致；需求文档变化后同步更新。

### 6. 做跨产物一致性验收

逐项对照脑图、系统策划需求文档、Figma 和 Demo：

- 核心循环、消耗与产出是否一致。
- 倍率、概率、合成、升级、失败与上限规则是否一致。
- 所有关键按钮、弹窗、自动行为与异常提示是否有对应规则。
- 每条关键需求是否能追溯到脑图、Figma、Demo、配置、埋点和 QA；不适用映射是否说明原因。
- Debug 是否能恢复真正的初始状态。
- GitHub 部署入口、相对路径和移动端尺寸是否有效。
- `index.html` 引用的每个脚本、样式和资源是否真实存在、使用项目相对路径并包含在上传/提交清单中；Git 仓库内同时检查 `git status`、`git ls-files`、HTTP 状态与 MIME。
- 体验说明是否能让首次体验者在 30 秒内完成一次核心操作，且没有把未实现功能写成已完成。

若不一致，先修脑图与系统策划需求，再同步其余产物。最终报告明确列出已实现、仅展示、仍是假设和未实现项。

## 知识库维护

将稳定的 Merge 元玩法知识写入 [merge-meta-knowledge.md](references/merge-meta-knowledge.md)。只在用户明确要求“记入/更新知识库”，或已经用真实产品信息确认时更新。

将跨活动可复用的类型判断、制作方法、成本变量和类型特有风险写入 [gameplay-event-knowledge.md](references/gameplay-event-knowledge.md)。单次活动的部位数、周期、奖励、表现和成功数据不能自动升级为类型规则；旧项目“数据不错”只有在记录产品、人群、指标、时间窗和对照口径后，才能提升为可迁移证据，否则保持为经验假设或待验证。

每条新增知识必须包含：

- 结论或规则
- 适用范围与反例
- 状态：`产品事实 / 外部事实 / 经验假设 / 待验证`
- 来源或形成依据
- 更新时间
- 对 UX、数值或实现的影响

发现冲突时保留冲突记录并说明优先级，不静默覆盖。优先级为：真实项目数据 > 用户确认的产品规则 > 可核实一手资料 > 竞品观察 > 经验判断。
