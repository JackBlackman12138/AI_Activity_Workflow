# Demo 工作流与多模型选择

## 当前平台结构（依据代码）

| 部分 | 实际职责 |
| --- | --- |
| apps/web | React + Vite 工作台；策划、配置、生成进度、隔离预览和对话修改 |
| packages/api | HTTP 接口、任务执行、模型网关、编译、浏览器验证与交付打包 |
| packages/shared | 活动/任务/配置类型、五阶段定义、Demo SDK 与存档桥 |
| packages/worker | 目前只有 JobHandler 接口，尚未运行独立任务队列 |
| packages/database | Prisma 数据模型，当前 HTTP 运行时实际使用 JSON 存储 |
| skills/demo | 平台实施规范和交互参考，通过 stage-guidance 选择性加入模型上下文 |

主流程：活动原稿 → 策划与配置 → Demo → UE 联调 → 程序交付。生成任务在 API 进程执行，浏览器轮询任务状态。data/runtime.json 没有业务记录时，继续兼容 packages/api/data/runtime.json；DATA_FILE 可以显式指定路径。

## 已核实的问题

1. 主流程要求多文件工程，但实际加载的 Demo 参考仍要求单 HTML、禁止 import/export，存在指令冲突。
2. 原实现把整套源码和测试放在一次模型输出中，复杂活动容易触及网关输出限制；原检查点无法保存其中已经完成的文件。
3. 真实扭蛋候选的供券场景从全新页面直接点击 #debug_button，没有进入活动。两个运行环境均可复现超时；原修复协议不允许补齐测试前置动作。
4. 多模型配置已有基础，但生成和对话接口只选全局默认模型，没有本次选择与任务绑定。
5. 源码 ZIP 原本只在最终程序交付阶段提供，功能与源码位置缺少统一的可读索引。
6. 工程内联使用字符串替换时，源码中的 $& / $$ 会被误解释成替换指令；已改为回调替换，并用真实编译执行验证。

## 新生成流程

用户点击一次，平台自动完成以下步骤，不增加中间审核表单：

1. 从确认的策划图文与现有配置整理需求、界面、演示假设。
2. 制定工程文件清单：职责、需求 ID、依赖顺序、导出接口和测试定位器。
3. 按文件生成。每个请求带完整业务规格、文件接口约定与已完成依赖源码；每个完整文件立即保存到任务检查点。
4. 根据实际源码分组编写试玩场景。每个场景从首次进入的全新页面独立开始。
5. 使用现有 esbuild 编译，在平台沙箱及离线页面中运行 Playwright 场景。
6. 基于真实结果核对业务与截图，最多四轮局部修复并重新测试。未通过的工程继续保留为候选，不能覆盖已保存版本。
7. 保存验证通过的源码、配置与记录。下载时从同一版本生成 Markdown 功能规格及完整源码包。

这次沿用现有 OpenAI-compatible Chat Completions 网关，不接入新的账号或 Codex SDK。封装的是“任务规范 → 写文件 → 工具验证 → 诊断 → 修复 → 交付”的执行流程；模型本身不拥有宿主 shell，也不会执行上传插件里的脚本。没有直接搬运 Codex 桌面插件服务或宣称已经接入 Figma、图像生成。

## 可见进度

- 当前任务绑定的模型与具体生成操作。
- 源码完成数量、已保存文件目录和可展开的源码内容。
- 每项真实试玩的通过/失败状态；失败时记录原因及实际页面文字。
- 每轮问题摘要、实际修改的文件与补齐的场景数量。
- 暂停后已完成文件保留；恢复同输入的任务继续未完成部分。切换模型或输入版本会按任务签名重新生成。
- 记录为工具结果与工作摘要，不展示或伪造模型私有思考。

## 模型选择

在模型中心添加并启用多个配置。工作台的“本次生成 / AI 修改使用的模型”选择器决定新的生成任务和对话修改请求。

POST /api/generation-jobs 和产物 refine 接口接受可选 modelId。任务创建时保存 modelId/modelName；没有显式选择时绑定当时的默认可用模型。执行不随全局默认变化而串模型；指定模型被停用或删除会明确失败，不静默换用其他模型。

原模型继续：使用“继续生成/继续自动修复”。切换后继续：选择其他模型并点击“改用所选模型继续”。恢复接口支持可选 modelId。密钥仍只保存在原有服务端加密字段中。

## 测试修复规则

保留原有回归场景的全部动作、需求 ID 和结果断言。新增 testSetups 协议只允许在已有场景前面增加 click/fill/select 前置动作，不允许删除、替换或降低断言。新场景仍通过 tests 新增。

这解决了“测试误以为页面继承上一个场景状态”的卡点；不能用它掩盖业务错误或直接完成活动内部玩法。

## 源码和 Markdown 交付

Demo、UE 联调和程序交付阶段分别提供 demo.zip、ue-demo.zip、handoff.zip。版本或验证不匹配时拒绝导出已认证工程。

| 路径 | 用途 |
| --- | --- |
| project/ | 全部原始源码，保留原文件路径，开发修改入口 |
| standalone.html | 自带运行配置的独立试玩快照 |
| project-files.json | 全部源码路径清单 |
| project-tests.json | 保存的浏览器回归场景 |
| configuration.json | 可编辑的完整配置 |
| docs/features.md | 功能规格：来源、验收、源码文件/行号、配置表、操作步骤、实际测试结果 |
| docs/requirements.json | 同一份结构化需求与配置计划 |
| docs/planning.md | 确认的策划原文 |
| docs/configuration.md | 配置字段字典 |
| docs/quality.md | 检查记录、演示假设与待确认项 |
| docs/implementation.md | 本阶段程序交接说明 |
| tools/ + package.json | 重建配置、编译源码、浏览器回归与本地预览 |
| manifest.json | 导出文件校验信息 |

开发流程：npm install → 修改 project/ 和 configuration.json → npm run build → npm test → npm start。新增源码路径加入 project-files.json。src/ 是导出快照，不作为多文件工程的修改入口。

## 验证范围

自动化覆盖文件检查点与断点恢复、多文件编译、浏览器交互、对话局部修改、测试前置步骤、模型绑定、导出重建和已有平台功能。真实扭蛋供券失败场景已用原候选代码复现，补齐入口动作后两个环境均通过；这不等于整个历史扭蛋项目通过验收。

生产网关的长任务输出与美术效果仍需实际活动生成验收；本次代码测试使用可控模型响应，不把测试样例的通过冒充真实模型整体效果。
