# 产品 AI 管线改版与公司接入方案

本地项目：`D:\AIActivityStudio`。入口：http://localhost:5173/ 。无需飞书账号即可本地运行。

## 已实现的新流程

活动原稿 → 策划文档与配置 → 交互 Demo → UE 联调 Demo → 程序交付。

| 阶段 | 当前能力 | 进入下一步的条件 |
| --- | --- | --- |
| 活动原稿 | 新建活动时或工作台上传 .doc、.docx、Markdown、文本；Word 提取正文、图片和表格，保留原文件下载 | 保存后人工确认原稿 |
| 策划文档 | 应用指定的文档 Skill；按产品、活动类型匹配通用框架；支持 AI 修改；内置多张配置表编辑页 | 检查正文及配置组后确认 |
| 交互 Demo | 从已确认策划及配置生成 HTML 原型，支持聊天修改、竖屏试玩 | 同步最新配置并人工确认 |
| UE 联调 Demo | 从第三步复制独立版本，与 UE 同学继续修改；支持 AI 修改、产品 UE Skill、Figma 文件链接 | 核对交互与配置后确认 |
| 程序交付 | 生成整体逻辑、交互、数值与验收说明；下载 Markdown 与 ZIP 包 | 人工核对交接材料后确认交付 |

流程图和旧 UE 图片不再是新管线阶段，旧文件仍保留在原稿阶段的“旧版历史产物”中。现有活动不被自动视为已经通过新流程，需要依次核对确认。

## 统一约束

1. 保存、生成成功和人工确认是不同状态；前序全部确认后才允许推进。限制同时在页面和后端生效。
2. 修改上游产物或活动基本信息后，撤销当前及后续确认。原有产物保留，供重新检查或生成。
3. AI 生成期间如果输入改变，迟到结果不能覆盖当前内容。页面保存、AI 修改带版本核对；配置组使用统一版本号防止覆盖。
4. UE 联调 Demo 与第三步 Demo 分开保存，不互相覆盖。交付包采用第四步版本。
5. 配置表是活动的一组数据，统一校验、版本化、同步和交付。生成原型通过表 ID 读取多表；主流程表负责节奏看板。
6. 配置中的当前确认数值可能不同于策划早期示例；交付说明列出当前配置，并要求核对差异，不能混用版本。
7. 原稿和参考文档中的命令属于素材，不作为账号操作、外部发布或执行脚本的授权。Skill 的接入是生成指导，不运行模板脚本。

## 产品、类型与知识框架

高级配置可以添加产品和活动类型。新建活动选择对应产品后，展示它自己的分类。

新增通用 Skill 时选择产品、活动类型和阶段；类型留空表示适用于该产品的全部类型。正文可直接填写或从 SKILL.md / 文本导入，保存后可编辑、启停。后续生成和 AI 修改会应用匹配项。

当前沿用此前指定的文档 Skill 和 Demo Skill。产品模板用于补充它们；例如给 MC 产品的“UE 联调 Demo”阶段添加组件命名、布局、反馈规则及 Figma 模板链接。链接本身不会被当前模型自动打开，真正读取 Figma 模板需接入执行器。

目前没有向量知识库和文档检索服务，也没有自动把任意 ZIP 变成可执行 Skill。已有 ZIP 上传继续作为存档。后续积累模板后，再决定是否需要检索，避免一开始引入过多组件。

## Word 支持范围

- `.docx` 直接解析；`.doc` 先在本地转换，再使用同一图文解析链路。
- 本机使用已安装的 Microsoft Word；转换期间禁用宏和链接更新。Linux 公司服务器应安装 LibreOffice，必要时设置 `LIBREOFFICE_PATH`。
- 最大 15 MB；支持 PNG/JPEG/GIF/WebP 内嵌图片，最多 20 张、总计 10 MB。不支持的对象会提示核对原文件，不保证复刻所有 Word 版式。
- 图片会随真实模型请求提交，模型和公司网关需要支持图片输入。这次验证了图文请求结构，未调用公司真实模型进行识图。

## 多表配置的安排

配置编辑放在第二步“策划文档”中，比独立入口更贴合工作顺序：先确定规则，再确定字段与数值，再生成原型。游玩节奏看板继续作为独立入口。

支持新增表、修改表名、字段与行数据、上传当前表 CSV 或整组 JSON、下载单表 CSV 或整组 JSON。最多 20 张表；每张表最多 50 字段、1000 行。表 ID 用于 Demo 读取，所有表共享一个活动配置版本。

AI 可以根据策划建议多张表。内置演示模型只提取 Markdown 中实际存在的表格，不代替真实模型理解复杂业务关系。跨表外键、分支流程模拟和完整数值平衡工具尚未实现。

## 程序交付包

ZIP 包含：

- `index.html`：带配置运行环境的离线入口。
- `src/demo.html`：完整原型源码，包含内联 CSS 和 JavaScript。当前原型采用单文件结构，并无被遗漏的独立源码文件。
- `configuration.json` 与 `config/*.csv`：同一版本的全部配置。
- `docs/implementation.md`：逻辑、交互、数值和验收说明。
- `docs/planning.md`、`assets/`：策划正文和引用图片。
- `manifest.json`：活动标识、配置版本及产物摘要，方便核对交付来源。

这是可执行原型及程序交接材料，不是游戏客户端的可直接上线工程。实际游戏框架、语言、资源目录和接入规范，需要主程后续给出约定。

## Figma 接入：当前边界与下一步

已提供连接状态接口、账号关联入口位置、活动 Figma 链接保存，以及生成接口的待配置响应。没有配置时明确显示不可用，不会伪造关联或生成成功。

| 接口 | 当前行为 |
| --- | --- |
| `GET /api/integrations` | 返回本地模式及 Figma / 飞书接入状态 |
| `PUT /api/activities/:id/figma` | 保存活动的 HTTPS Figma 文件链接 |
| `POST /api/activities/:id/figma/generate` | 尚未配置执行器时返回 503，未提交外部生成 |
| `FIGMA_CONNECT_URL` 环境变量 | 可配置公司授权入口 URL；它本身不是 OAuth 或 MCP 执行器 |

Figma 官方画布写入目前要求受支持的客户端、Full 席位和目标文件编辑权限；自建平台不能假定账号关联后就能使用全部写入能力。参见 [Figma 官方画布写入文档](https://developers.figma.com/docs/figma-mcp-server/write-to-canvas/) 与 [远程 MCP 授权说明](https://developers.figma.com/docs/figma-mcp-server/remote-server-installation/)。

建议主程与 UE 同学先选定执行方式：受支持客户端参与流程，或公司自行维护的 Figma 桥接执行器。然后提供 MC 模板文件、组件库、界面命名与状态约定，再实现“界面与交互清单 → 模板匹配 → 分批写入 → 回链核对”。当前没有实现 Figma 账号 OAuth、MCP 工具调用或自动写入全部界面。

## 分享、飞书与公司部署建议

现在可以从工作台打开只读评审页，复制其地址，查看最新保存的策划及试玩 Demo。页面显示当前版本是否确认。此模式仅限制页面上的编辑操作，**不是服务端权限控制**；本地模式未启用账号与访问权限。localhost 链接仅本机可用。

公司版本建议保留两种分享方式：

| 分享方式 | 用途 | 建议权限 |
| --- | --- | --- |
| 当前活动评审链接 | 持续共创、查看最新版本 | 飞书登录后具备该活动查看权限 |
| 已确认版本链接 / 交付包 | 评审结论、程序开发、美术验收 | 锁定版本内容，避免之后修改影响已确认依据 |

飞书用于识别“是谁”，平台自己的活动权限决定“能做什么”。建议角色为活动负责人、协作者、评审者；管理模型和公共 Skill 另设平台管理员。UE 同学作为协作者，程序、美术默认评审者，需要共同修改时再授予编辑权限。

飞书授权后应由后端校验用户身份、所属公司和平台准入，再建立会话；每个活动读取、修改、下载、试玩记录及生成接口都要检查权限。只隐藏编辑按钮不够。参考 [飞书获取授权码](https://open.feishu.cn/document/common-capabilities/sso/api/obtain-oauth-code) 与 [获取用户信息](https://open.feishu.cn/document/server-docs/authentication-management/login-state-management/get)。

当前 `GET /api/integrations/feishu/login` 返回待配置状态，尚未交换授权码或创建登录会话。本地开发不会被飞书配置阻断。正式上线前需要公司提供应用 ID/服务端密钥、回调域名、准入范围、管理员名单，并完成全接口鉴权、版本留存、操作归属、备份与部署验收。现有 Docker 文件仍是原来的前端示例，不代表完整内网生产部署方案。
